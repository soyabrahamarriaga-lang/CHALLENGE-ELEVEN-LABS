# ADR-0011: Bóveda Obsidian privada para transcripciones y notas del agente

- Fecha: 2026-10-03
- Estado: aceptada
- Autor: Claude; operador: soyabrahamarriaga-lang
- Sustituye / sustituida por: amplía ADR-0010 (antes UserHelper no conservaba transcripciones)

## Problema y evidencia
El usuario pidió «instalar Obsidian como la base de datos para que ahí se guarden las transcripciones y archivos que genere el agente de Eleven» y conectarlo al resto. Eligió explícitamente: bóveda sincronizada con un repo GitHub **privado** aparte, instalar Obsidian en su Mac y trabajar en una rama separada mientras el equipo integraba el agente. Este repositorio es **público**; las transcripciones contienen voz y datos de personas.

## Alternativas
- Guardar sesiones dentro de este repo: expone datos personales en un repo público y viola ADR-0002 (solo código y contexto).
- Plugin Local REST API de Obsidian: exige la app abierta y un plugin de terceros; frágil para la demo.
- Base de datos (SQLite/Postgres): más infraestructura; el equipo pidió Obsidian para leer y enlazar notas.
- Obsidian Sync (de pago) o bóveda solo local: descartadas por el usuario en favor del repo privado.

## Decisión y razón
La bóveda es una carpeta de Markdown fuera del repo (`VAULT_PATH`, ruta absoluta) sincronizada con `github.com/soyabrahamarriaga-lang/userhelper-vault` (privado). `server/vault.mjs` es el único escritor; Obsidian solo la visualiza. `server/main.mjs` monta la bóveda junto al acceso LiveKit/ElevenLabs existente en el mismo proceso (`npm run dev:token`).

- `POST /api/vault/conversations/:id/import`: el backend obtiene la conversación terminada de ElevenLabs con la API key del servidor y escribe `Sesiones/<fecha>-<id>/transcripcion.md` con frontmatter. 409 mientras ElevenLabs la procesa; el cliente reintenta.
- `POST /api/vault/sessions/:id/events`: añade eventos (pantalla, pregunta, respuesta, guardrail, decisión, nota) a `eventos.md`. Preparado para client tools y visión; todavía nadie lo llama.
- `POST /api/vault/sessions/:id/notes/{work-map|debrief|teach-back}` y `GET /api/vault/sessions`.
- Sincronización periódica (`VAULT_SYNC_MINUTES`, 2 por defecto): el backend lista las conversaciones del agente configurado y guarda las terminadas que falten. Es el mecanismo principal porque no requiere URL pública y cubre conversaciones iniciadas fuera de la app; el usuario pidió que se guarden las transcripciones del agente, no solo las de una pantalla.
- `POST /api/elevenlabs/webhook`: webhook post-llamada firmado con HMAC (`elevenlabs-signature`), opcional; requiere URL pública.
- La vista del agente archiva automáticamente al terminar si la bóveda está configurada; si no, no muestra nada.

Controles: origen exacto como en LiveKit, JSON obligatorio, IDs `[A-Za-z0-9_-]{1,80}`, notas en lista cerrada, comprobación de ruta dentro de la bóveda, escritura atómica, límites de tamaño, errores opacos al cliente y logs por nombre de variable sin valores.

## Consecuencias
- El aviso de consentimiento cambia: ya no afirma que UserHelper no guarda mensajes; informa la copia en la bóveda si está activa.
- Sincronizar es manual (`./sync.sh` en la bóveda). Dos personas escribiendo a la vez pueden generar conflictos de Git en la bóveda; cada sesión vive en su propia carpeta para reducirlos.
- La firma del webhook se implementó según el formato `t=…,v0=HMAC-SHA256("t.body")` documentado por ElevenLabs para sus SDKs; no se ha probado contra un envío real.
- No hay redacción de datos personales (Presidio) ni flujo de retiro desde la UI: retirar = borrar la nota en la bóveda y revisar qué Work Map la cita. Ambos siguen pendientes para TRUST-01.

## Impacto ontológico
Sin cambio en `ontology.json`: la bóveda es almacenamiento de `session`, `evidence` y `work_map` ya definidos. Una transcripción guardada sigue sin ser razón validada ni Work Map confirmado.

## Verificación
Pruebas `server/vault.test.mjs` y `src/services/vault.test.ts`; escritura real en la bóveda local con una sesión marcada como sintética. Resultados en la entrada del aporte.
