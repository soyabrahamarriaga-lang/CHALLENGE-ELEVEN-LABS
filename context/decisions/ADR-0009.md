# ADR-0009: transporte LiveKit y acceso a sala desde backend

- Fecha: 2026-10-03
- Estado: aceptada para integrar videollamadas; sustituye el límite «solo frontend» de ADR-0008 únicamente en este recorrido
- Autor: Codex; operador: soyabrahamarriaga-lang
- Evidencia: el usuario solicitó evaluar e integrar livekit-client, inicialmente pidió dejar configuración preparada y después creó un proyecto LiveKit Cloud y guardó sus credenciales localmente.

## Problema y decisión

El prototipo necesita comunicación real de voz, video y pantalla entre participantes. Adoptar `livekit-client` para el transporte WebRTC y `livekit-server-sdk` en un pequeño servicio Node para emitir tokens temporales. Mantener una vista propia de videollamada y conservar la biblioteca de demostración identificada como sintética. Cargar el SDK del cliente al abrir esa vista.

Las claves del proyecto permanecen en el backend. Un código de equipo, origen autorizado y consentimiento limitan el endpoint del hackathon; el servidor impone nombre de sala e identidad única, con permisos de publicación específicos y tokens de cinco minutos. No se permite al cliente elegir otra sala, identidad privilegiada ni permisos adicionales. El selector senior/intern sigue siendo demostrativo, sin autenticar roles.

Entrar no activa dispositivos. Cada fuente exige una acción explícita. Pausa, salida e interrupción de red detienen pistas físicas incluso cuando falla la señalización. Reconectar o continuar nunca reactiva dispositivos automáticamente. Cancelaciones invalidan resultados tardíos de token, conexión y permisos. No se captura audio del sistema.

## Alternativas y consecuencias

- WebRTC directo: requeriría señalización y operación de conectividad adicionales bajo el plazo disponible.
- Token fijo o API secret en frontend: expone permisos reutilizables o las claves del proyecto; descartado.
- Solo preparar variables: no permitiría verificar acceso, participantes y ciclo de vida en la experiencia solicitada.
- LiveKit con endpoint propio: reutiliza transporte y permisos por sala; añade un proceso backend que debe desplegarse junto al frontend.

El código compartido no sustituye autenticación individual. Se documentan HTTPS/proxy, origen exacto, límites de intentos en memoria y trabajo pendiente de autorización para producción. El SDK aumenta el tamaño de la descarga de videollamada; el recorrido de biblioteca no lo carga inicialmente. No se inicia Egress, almacenamiento de medios, conexión ElevenLabs ni generación de Work Map.

## Ontología

Se añaden sala de comunicación y pista multimedia. Una pista transportada no equivale a un evento visual interpretado, evidencia conservada ni razón del experto. Estar conectado a una sala tampoco demuestra conexión del AI Apprentice ni cumplimiento de Capture. Se mantienen independientes consentimiento, captura local, transporte, agente y conocimiento validado. El esquema ontológico conserva versión 1.

## Validación y relevo

Pruebas de token firmado y permisos; pruebas del controlador con dispositivos simulados; build estricto; acceso real a Cloud y navegador. Los resultados precisos y las limitaciones quedan en la bitácora del aporte. La prueba de audio/video/pantalla entre dos computadoras con permiso de sus operadores sigue siendo necesaria, así como agente, visión, debrief y Map/Teach. Configuración y contrato en docs/LIVEKIT.md.
